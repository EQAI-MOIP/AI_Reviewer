# AI 심사팀장 큐리 v3.0.0

**출원번호 또는 직접 준비한 문서를 바탕으로 심사 검토사항을 원문·판본·규칙과 대조하는 HTML/JavaScript 앱입니다.** 앱 안에서 사용자는 ‘심사관님’, 캐릭터는 ‘AI 심사팀장 큐리’로 안내합니다.

이번 버전은 사용자 제공 `AI_Review_Leader_QURI_v2.0.0(1).zip`을 개선했습니다. 외부 CDN·웹폰트·npm 패키지·LLM SDK를 실행 의존성으로 추가하지 않았습니다. HTML/CSS/JavaScript와 포함된 WebP만 사용하며, 선택적 로컬 API 실행 도우미도 Node.js 기본 모듈만 사용합니다.

## 1. 빠르게 시작하기

1. ZIP 전체를 한 폴더에 압축 해제합니다. ZIP 안의 `index.html`만 따로 실행하지 마세요.
2. 화면·예시·직접 문서 추가를 확인하려면 `index.html`을 엽니다.
3. API를 안정적으로 연결하려면 Node.js 22 이상이 준비된 컴퓨터에서 `start-windows.cmd`를 실행하거나 아래 명령을 실행합니다. Node.js 자체는 포함되어 있지 않습니다.

```bash
node server.js
```

4. 표시된 `http://127.0.0.1:8765`를 브라우저에서 엽니다. 다른 포트가 필요하면 `node server.js --port=8766`을 사용합니다.
5. 설정에서 LLM Base URL, 정확한 모델 ID, API 키와 방식을 입력합니다. 출원번호 조회를 이용할 때는 KIPRIS Plus 키도 입력합니다.
6. **설정 적용** 후 ‘모델 목록 연결 확인’, ‘실제 텍스트 호출 확인’, 필요하면 ‘PDF 판독 연결 확인’을 실행합니다. 실제 생성 확인 두 가지는 합성 자료만 전송하지만 API 비용이 발생할 수 있습니다.
7. ‘내 문서로 진단’에서 서류를 추가하거나 ‘출원번호로 조회’에 번호를 입력합니다. 상단 **큐리와 둘러보기**에서 실제 입력 위치를 안내합니다.

모델 목록이 반환되는 것과 실제 생성·PDF 입력이 가능한 것은 서로 다른 확인입니다. PDF 판독 연결 확인에 성공해도 실제 업무 문서의 한글·수식·표 정확성을 보증하지 않습니다.

## 3. 토큰과 호출 설정

| 항목 | 기본값 | 주의할 점 |
| --- | ---: | --- |
| 요청 전체 토큰 예산 | 128,000 | 입력 + 출력 예약 + 안전 여유의 합. 실제 모델의 컨텍스트 한도 이하로 지정 |
| 요청당 최대 출력 | 32,768 | 추론 토큰도 포함될 수 있음. 실제 모델의 출력 한도 이하로 지정 |
| 한 호출 최대 대기 | 300초 | 설정에서 30~900초. 중단 버튼으로 취소 가능 |
| 진단 실행당 AI 호출 상한 | 100회 | 전사·요약·규칙 검토·반론 검토·실패 재시도 포함. 1~300회 설정 가능 |
| 한 요청의 규칙 수 | 최대 3개 | 입력 예산이나 출력 잘림에 따라 더 작게 나눔 |
| PDF 전사 요청 범위 | 기본 2쪽 | 출력 잘림 시 1쪽으로 축소 |

출력 32k는 사건 전체 보고서의 길이 상한이 아닙니다. 여러 요청의 결과를 합칩니다. 상한이 커도 언제나 그만큼 생성되는 것은 아닙니다. 상한 증가·반론 검토·분할 재시도로 시간과 API 사용량은 늘어날 수 있습니다. 호출 수 상한은 금액 상한이 아니며 입력 토큰 계산 요청은 별도입니다.

모델 세대 이름만으로 엔드포인트나 모델 ID를 추정하지 않습니다. Responses는 `/v1/responses`, Chat Completions는 `/v1/chat/completions`를 사용합니다. 공식 OpenAI Responses와 PDF 입력은 입력 토큰 계산을 먼저 수행합니다. PDF 토큰을 계산할 수 없는 호환 서버에서는 추정치로 자동 진행하지 않습니다.

## 4. 어떤 문서를 읽나요?

| 형식 | 읽기 방식 | 결과를 확정하기 전 필요한 확인 |
| --- | --- | --- |
| PDF | 로컬 텍스트 추출. 불완전하면 지원 모델에 PDF 원문을 보내 쪽별 전사 | 스캔·그림·수식·표·식별자의 실제 원문 대조. 미판독 쪽은 확인 체크로 우회 불가 |
| HWPX | ZIP 내부 XML을 패키지 `spine` 순서대로 읽고 문단·표·셀 위치 보존 | 물리적 인쇄 쪽수, 그림·수식·자동 번호 등. 같은 판본 PDF 병행 권장 |
| DOCX | 본문·표·각주·미주·머리말·꼬리말 텍스트 | 실제 쪽 배치, 수식·그림·자동 번호·숨김·변경 추적 표현 |
| TXT·MD·JSON | 텍스트 인코딩을 확인해 추출. `[쪽 n]` 구분 지원 | 문서 식별·시점·원본 전체성. 링크에 있는 외부 자료는 자동 열람하지 않음 |
| 구형 HWP·DOC | 직접 판독하지 않음 | 원래 편집기에서 HWPX·DOCX 또는 PDF로 저장 |

**HWPX·DOCX의 텍스트 추출 성공을 원문의 모든 내용과 쪽수가 확인된 것으로 취급하지 않습니다.** 구조 위치와 누락 요소는 ‘분류·원문 확인’에서 볼 수 있습니다. 정확한 쪽 인용·전체 문언 확인이 필요한 판단에는 같은 판본의 PDF 또는 원문과 대조한 쪽 표시 텍스트를 함께 준비하세요.

PDF 전사는 모델의 오류 가능성이 있으므로 전사 뒤에도 원문 확인이 필요합니다. 전사에 실패한 쪽은 일반 재진단 시 그 쪽만 재시도하고, 성공한 쪽은 재사용합니다. 전사가 끝나고 시각 확인만 남은 문서는 재전사하지 않습니다.

**PDF 쪽 범위 요청은 실제 파일 분할이 아닙니다.** 매 요청에는 원본 PDF 전체가 전달되어 입력 토큰이 반복될 수 있습니다. 큰 스캔 PDF가 모델의 입력 한도를 넘으면 원래 PDF 도구에서 쪽 범위별 파일로 나누어 추가해야 합니다.

상세: `docs/DOCUMENTS-V3.md`, `docs/DIAGNOSIS-V3.md`.

## 5. 자료는 어디에 저장되나요?

| 자료 | 보관 위치와 정리 방식 |
| --- | --- |
| KIPRIS에서 수집한 원문·직접 추가한 문서·추출문·진단 결과 | 현재 브라우저 탭의 메모리. 앱이 디스크·localStorage·IndexedDB에 자동 보관하지 않음 |
| PDF 미리보기 | 현재 탭의 임시 Blob URL. 닫기·사건 교체·비우기에서 해제 |
| 실행 도우미가 중계하는 키·문서 | 요청 처리 중 메모리만 사용. 디스크에 업무 문서·키·요청 URL을 기록하지 않음 |
| ‘원문 저장’·‘사건 저장’·‘보고서 저장’으로 내려받은 파일 | 브라우저에 설정된 다운로드 위치. 보통 운영체제의 다운로드 폴더이며 앱이 경로를 결정하거나 자동 삭제할 수 없음 |
| LLM에 전송한 자료 | 선택한 API 제공자의 데이터 처리 정책 적용. `store:false`만으로 제공자의 모든 기록이 삭제된다고 보증하지 않음 |

**새 사건 조회**, **이전 자료 정리·새 사건**, 정상적인 **사건 불러오기**는 이전 사건의 임시 자료를 정리합니다. 가져오기가 실패하면 기존 사건은 유지합니다. 예시를 보는 동안만 실제 사건 하나를 임시로 보존하며, 명시적 비우기는 이 백업도 정리합니다. 같은 사건에 서류를 추가하거나 재진단할 때는 현재 자료를 유지합니다.

필요한 결과는 새 사건을 시작하기 전에 저장하세요. 앱의 정리는 자바스크립트 참조와 임시 URL을 해제하는 것이며 운영체제 메모리를 강제 소거하거나 즉시 정확한 양의 RAM을 반납한다고 보장하지 않습니다.

### 용량 한도

- 개별 원문 30 MiB, 한 사건 150개, 원문 바이너리 합계 180 MiB.
- 문서별 본문 200만 자, 사건 전체 본문 1,000만 자.
- 사건 JSON 저장·가져오기 100 MiB. 원문은 Base64로 포함되어 원본보다 커집니다. 큰 사건은 보고서·원문을 각각 저장하고 사건을 나누세요.
- 화면 용량은 **보관 원문 크기**이며 브라우저의 전체 RAM 사용량이 아닙니다. 추출문·화면·압축 해제·Base64 처리의 메모리는 별도로 필요합니다.

## 6. 정확한 진단을 위한 준비

현재 설치된 **AI 품질진단 시스템 2026.11.12 / diagnostic / portable**의 원문과 포함 규칙이 동일한 것을 확인했습니다. OA 17개, RD 6개, RC 7개와 공식 진단코드 84개를 포함합니다. `APIKEY.md`와 개인 키는 배포하지 않습니다.

진단에는 다음 자료가 중요합니다.

1. 각 통지 당시의 전체 청구범위와 보정 접수 순서.
2. 통지서·최후통지·결정서 전체 및 사건의 행정처리 이력.
3. 기재요건 판단에 필요한 발명의 설명·도면의 해당 시점 판본.
4. 실제 인용문헌 원문과 문헌번호·문단·도면의 일치.
5. 등록 건은 최종 유효 등록청구항 전체와 인용관계.
6. 적용 시점의 공식 법령·기준 및 사람이 확인한 쟁점 기록.

각 문서에서 ‘원문을 확인했다’는 항목은 실제로 대조한 경우에만 선택하세요. 한 체크박스로 누락된 원문·미판독 쪽·확인되지 않은 판본을 생성할 수 없습니다. 확인되지 않은 주장은 조건부 또는 확인 불가로 유지됩니다.

앱의 API 호출만으로 ChatGPT Work의 파일 실행·검색·브라우저 도구가 자동으로 붙지는 않습니다. 필요한 단계를 코드로 구성했지만 모든 문헌·현행 법령의 범용 자동 검색을 포함하지는 않습니다. 이번 제작에서는 개인 API 키를 이용한 실제 출원 운영 진단이나 기존 Work 모드와의 동등 정확도 시험을 수행하지 않았습니다.

## 7. 확인한 범위와 배포 파일

검증 기록은 `docs/VALIDATION.md`, 기계 판독용 결과는 `tests/validation-results.json`에 있습니다. 단위시험과 DOM 이벤트 시험, 실제 브라우저 렌더링, 실 API 검증을 구분합니다. 이번 환경에서 실제 브라우저 화면 검증은 완료하지 못했습니다.

```bash
node --test tests/*.test.cjs
```

기본 시험은 Node.js 기본 모듈을 사용합니다. HWPX·DOCX XML 어댑터 시험은 Python 표준 라이브러리를 선택적으로 사용하며 없으면 해당 시험만 건너뜁니다. 네이티브 Chromium 시험은 Playwright 개발 도구가 설치된 시험 환경에서 `QURI_NATIVE_PARSER_TESTS=1`로 별도 선택합니다. 앱 사용에는 Python·Playwright·npm 설치가 필요하지 않습니다.

- `index.html`, `css/`, `js/`: 앱 소스.
- `assets/`: 기존 큐리와 새 16프레임 WebP.
- `rules/`: 기준 규칙 원문과 진단코드.
- `docs/IMPROVEMENTS-V3.md`: 여섯 가지 요청의 검토·반영 결과.
- `docs/SPRITES-V3.md`: 새 애니메이션의 프레임·접근성·검증 범위.
- `server.js`, `start-windows.cmd`: 선택적 로컬 실행 도우미.
- `tests/`, `examples/`: 재현 시험과 합성 예시. 실제 업무 문서는 포함하지 않음.
- `SHA256SUMS.txt`: 배포 파일의 SHA-256.
