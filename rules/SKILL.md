# AI 품질진단 시스템 — 무연결형

ChatGPT Work에서 실행한다. 설치 전에 사용자가 이 스킬의 `SKILL.md`와 같은 폴더에 있는 `APIKEY.md`의 `KEY=YOUR_KIPRIS_PLUS_API_KEY`를 본인 키로 교체하고 ZIP을 다시 압축하여 등록한다. 이미 설치한 경우 수정한 패키지로 다시 업로드·갱신한다. 키를 넣은 패키지는 본인 설치에만 사용하고 다른 사람에게 배포할 때는 자리표시자로 되돌린다.

## 배포 식별과 연동

- 내부 스킬 이름과 폴더는 기존 설치 호환을 위해 유지한다. 표시 이름은 AI 품질진단 시스템이다. `skill.json`의 유형·버전·설정 보존 목록을 기준으로 업데이트하며, 개인 설정을 진단 규칙과 병합하지 않는다.
- 업데이트는 별도 `AI 품질진단 시스템 업데이트` 스킬을 사용한다. 진단 요청만으로 설치본을 변경하지 않는다. 정식 배포 전에는 기존 운영 설치본을 교체하지 않는다.
- 결과에 이 설치본의 `skill.json`에서 확인한 버전·유형을 적는다. 피드백용 요약에는 출원번호와 주요 진단사항(규칙 ID·코드·대상항·판정·핵심 근거·조건)을 연결하여 남긴다. 미확인 값은 생성하지 않는다. 요약을 사이트로 자동 전송하지 말고 별도 피드백 요청에만 등록한다.

## 1. APIKEY.md 키 확인과 KIPRIS Plus 조회

**기본 경로는 스킬의 APIKEY.md → KIPRIS Plus REST API → ChatGPT PDF 보관 → 진단**이다. 클라우드 브라우저에서 KIPRIS 화면을 여는 것을 선행 단계나 자동 대체 경로로 삼지 않는다. 요청 주소·파라미터·응답은 `references/kiprisAPI.md`를 따른다.

1. 현재 실행한 **이 배포용 스킬**의 루트에 있는 `APIKEY.md`를 매 작업마다 다시 읽는다. 경로는 이 `SKILL.md` 기준으로 해석하며 다른 설치본이나 과거 대화의 키를 재사용하지 않는다. 파일의 `KEY=값` 한 줄에서 값을 읽고 양끝 공백을 제거한다. 값이 비었거나 `YOUR_KIPRIS_PLUS_API_KEY`이면 호출하지 말고 APIKEY.md 수정·패키지 갱신을 안내한다. KEY 줄이 없거나 여러 개면 임의로 고르지 않는다. 파일이 누락되거나 접근할 수 없으면 해당 오류를 알린다. 키 파일의 전체 내용을 대화나 도구 결과로 출력하지 않고 요청 프로세스 내부에서 읽는다.
2. 사용자가 설정한 키는 `APIKEY.md`에만 보관하고 해당 실행의 인증 요청에 사용한다. 키·키가 포함된 URL·서명된 PDF 경로를 코드, 추가 로컬 파일, 명령행 인수, 로그, 대화, 보고서, 별도 ChatGPT 보관 파일에 복사하지 않는다. 전체 키 파일을 출력하는 읽기 명령을 사용하지 않는다. 필요하면 에코를 끈 프로세스의 표준입력 등으로 전달하고 응답·예외 출력에서 키와 URL을 가린다. HTTPS 엔드포인트를 우선한다. 연결·상품 권한·인증 실패를 구분하여 알리고 키 값을 대화에 보내 달라고 하지 않는다. 키가 있는 APIKEY.md 또는 설치 ZIP을 진단 산출물로 저장·공유하지 않는다.
3. 출원번호를 구분기호 없는 13자리로 정규화한다. 행정처리 이력을 전부 조회하고 페이지가 있으면 끝까지 순회한다. `documentTitle`, `documentDate`, `documentNumber`로 모든 의견제출통지서·최후통지·동등한 거절이유 통지·거절결정서·등록결정서를 날짜순으로 구분한다. 의견서·보정서도 시점 대조에 기록하되 통지서로 세지 않는다. 이력이 불완전하면 서류가 없다고 단정하지 않는다.
4. 통지서와 각 결정서의 전용 `pdfInfoV2`를 조회한다. 이력의 `documentNumber`와 PDF 응답의 `sendNumber`를 매칭하고 모든 해당 건의 `filePath`에서 실제 PDF를 내려받는다. 응답에 URL만 있는 상태를 다운로드 성공으로 보고하지 않는다. 등록 건의 공보·청구항 경로는 참조 파일의 미검증 사항을 확인하면서 사용한다.
5. 통지 당시 청구범위를 복원하기 위해 `references/kiprisAPI.md`의 **청구항 변동 이력** `amendmentHistoryInfo` 및 `amendmentHistoryDetailInfo`를 출원번호로 조회한다. 최초 청구항부터 각 통지서 **이전** 접수분까지 `신규`·`수정`·`삭제`를 시간순으로 반영해 당시 전체 청구항의 문언과 인용관계를 만든다. 행정처리 이력의 보정서 접수번호·일자와 API의 `receiptSendNumber`·`receiptSendDate`를 대조하고, 통지서 인용 문구와 복원 결과를 교차 확인한다. 공개공보는 공개 시점의 스냅샷이며 출원 당시 또는 통지 당시 판본과 동일하다고 가정하지 않는다. 등록공보도 사후 판본으로서 과거 통지의 원문을 대체하지 않는다. 해당 API의 응답이 없거나 상품 권한이 없다면 가능한 원문 보정서 경로를 확인하고, 확보하지 못한 청구항별 실체 판정은 보류한다.

## 실체 판단에 필요한 원문 확보

- 명확성·실시가능성·신규성·진보성 등 실체 판단에 추가 원문이 필요하다고 식별하는 즉시 확보를 시도하고, 확인한 원문을 해당 쟁점에 대조한다. 통지서·결정서 비교나 청구항 복원 성공만으로 이 단계를 종료하지 않는다.
- 발명의 설명·도면이 필요하면 `references/kiprisAPI.md`의 공개공보 PDF 경로로 조회하고, 관련 부분이 이후 보정됐는지 확인한다. 통지 또는 결정 당시 판본을 확인하는 데 보정서가 필요하면 청구항 변동 이력을 확보했더라도 접수일·접수번호로 접근 가능한 공식 원문 경로나 사용자가 제공한 자료를 확인한다. 공개공보를 당시 판본으로 간주하지 않는다.
- 인용발명 원문이 필요하면 통지서·결정서의 첨부를 먼저 확인하고, 미확보 시 문헌번호·종류코드로 공개 특허공보나 발행기관 원문 등 접근 가능한 출처를 조회한다. 문헌 식별자와 해당 쪽·문단·도면을 확인한다. 기존 인증 및 KIPRIS 웹 화면 사용 조건을 지킨다.
- 필요한 원문 또는 적용 판본을 확보하지 못해 판단을 유보할 때는 문서별 식별자, 시도한 경로, 구체적 실패 사유, 유보하는 쟁점을 보고한다. 미시도 상태를 확보 실패로 보고하지 않는다. 확보한 자료로 판단 가능한 항목은 계속 진단한다.

## 2. 원문 검증과 ChatGPT 보관

1. 각 PDF의 `%PDF-` 형식, 바이트 수, 쪽수, 첫 쪽의 출원번호·문서명·발송일·발송번호를 확인한다. 불일치·빈 파일·HTML 오류 응답이면 진단에 사용하지 않는다. PDF 스킬로 본문을 추출하고 표·수식·각주·문헌번호·흐릿한 부분은 페이지 렌더링으로 확인한다.
2. **등록결정서(특허결정서)는 직권보정이 있는 경우에만 저장한다.** 일반 등록결정서는 결정일·청구항 수 등 필요한 내용을 확인한 뒤 보관하지 않는다. 직권보정 유무는 결정서 본문·첨부를 확인하고, 확인할 수 없으면 저장 여부를 보류한다. 이 예외는 의견제출통지서·최후통지·거절결정서·등록공보의 보관에는 적용하지 않는다. 보관 대상인 검증된 PDF는 ChatGPT Library에 파일로 보관한다. 현재 환경의 Library 스킬과 파일 저장 도구를 사용하며 외부 저장 서비스 연결은 요구하지 않는다. 파일명에는 출원번호·문서명·발송번호를 넣고 공보처럼 발송번호가 없으면 공보번호 또는 기준일을 넣는다. 동일 이름의 파일이 있으면 출원번호·문서 식별자·크기와 가능하면 해시를 비교하여 같은 내용만 재사용하고 다른 내용은 별도 파일로 보관한다. 저장 도구가 반환한 파일 식별자·이름·크기와 성공 여부를 확인하고 결과에는 사용자가 열 수 있는 파일 링크를 제공한다. 로컬 sandbox 링크만 제시한 상태를 영구 보관 성공으로 보고하지 않는다.
3. 다운로드·파싱용 임시 사본과 사용자에게 제공할 파일을 구분한다. 보관 성공과 진단 완료를 확인한 후 임시 사본만 삭제하고 결과 링크가 가리키는 파일은 유지한다. ChatGPT 보관 도구가 없거나 저장에 실패하면 확보된 PDF로 진단을 계속하고 다운로드 링크를 제공하되 영구 보관 미완료를 알린다. 진단에 필요한 로컬 파일은 링크 제공 전에 삭제하지 않는다. 다운로드 실패·저장 실패는 해당 문서와 단계별로 표시한다. 사용자가 별도 보존·삭제를 지시하면 그 지시를 따른다.

API를 사용할 수 없으면 실패 원인과 확보 범위를 밝히고 사용자 제공 원문으로 계속할 수 있다. 사용자가 웹 조회를 별도로 요청한 경우에만 KIPRIS 웹 화면을 보조 경로로 사용한다. 어느 경로든 전체 문서 목록을 확인하지 못했다면 '없음'이나 '새 이유 없음'을 확정하지 않는다.

## 3. 의견제출통지서 각각의 내부 진단

- **각 문서를 독립적으로** `references/office-action-rules.md`의 OA 규칙 전부에 적용한다. 최후통지도 동일하게 살핀다. 한 통지서의 주문과 다른 통지서의 세부 이유를 섞어 내부 불일치라고 하지 않는다. 문서 내부 대조와 청구항 원문이 필요한 타당성 판단을 구분한다.
- 진단코드를 부여할 때는 `references/diagnostic-codes.md`의 공식 진단유형과 결정 경과별 조건을 읽는다. 제42조의 발명의 설명(`04xx`), 청구범위 기재요건(`05xx`), 시행령 제5조의 기재방법(`06xx`)을 구별한다. 특히 청구범위 기재요건 오지적은 거절결정과 다른 정당한 이유의 유무에 따라 `0512` 또는 `0521`이다.
- 문서마다 `심사대상 청구항`, `주문의 법조문·대상항`, `세부 이유별 대상항·인용발명 조합·결론`, `첨부문헌`을 표로 정리한다. 범위는 집합으로 펼치되 불명확하면 원문도 보존한다.
- 청구범위의 `바람직하게(는)`·`더/더욱 바람직하게(는)`·`특히`는 **OA-17**의 이중한정 기준으로 엄격히 점검한다. `임의로`·`선택적으로`와 혼동하지 않는다. 발명의 설명에만 있는 표현은 구별한다.
- 인용발명의 `조합`·`결합`은 OA-13에 따라 문맥으로 해석한다. 의미의 혼용·파악 불가에 따른 작성 문제와 구성 대비·용이도출 논증 부족을 구별한다.
- 통지서 오기는 OA-14와 진단코드 참조의 `1231` 적용 기준을 먼저 확인한다. 통지서만으로 오기와 올바른 의미를 명백히 알 수 있는 단순오기는 진단에서 제외하고, 인용발명 원문을 읽어야 확인·정정되는 오기는 고객지향성 관점에서 평가한다.
- 통지서의 주문·이유가 내부에서 일치하는지와 거절이유 자체가 타당한지는 구별한다. **모든 청구항별 실체 판단**에서 통지 당시 청구항 원문·인용관계·관련 종속항과 필요한 발명의 설명을 대조한다. 판본을 확보하지 못하면 통지서 인용부로 확인되는 범위와 확인 불가 범위를 구분하고 오지적·정당성을 확정하지 않는다. 외부 명세서·인용문헌의 진위를 별도로 조사하지 않은 범위는 명시하고, 공개공보 또는 사후 등록청구항을 통지 당시 판본으로 추정하지 않는다.

### 최후통지가 있는 경우: 보정으로 발생한 거절이유인지 필수 대조

- 최후 의견제출통지서가 있으면 결정 종류와 관계없이 `references/office-action-rules.md`의 **OA-15**를 반드시 적용한다. 보정으로 발생하지 않고 최초 심사대상 판본부터 존재하던 거절이유를 최후로 통지한 경우를 중점 검출한다.
- 최후통지의 각 이유별로 보정 전후 전체 청구항·인용관계와 선행 통지를 대조하고, `보정에 따른 발생 / 보정 전부터 존재 / 확인 불가` 및 판단 근거를 결과에 명시한다. 새 문헌·새 법조항·두 번째 통지라는 사실만으로 최후통지라고 인정하지 않는다. 확정된 혼동은 `1024`, 최초부터 있던 이유의 분할 통지는 `1031`의 요건을 별도로 확인한다.

## 4. 결정 종류에 따른 진단

### 거절결정서가 있는 경우

- 완전하게 조회한 행정처리 이력에 거절결정서가 **없으면** `거절결정서: 행정처리 이력에서 확인되지 않음`이라고 보고하고 이 단계는 생략한다. 있으면 `references/rejection-decision-rules.md`의 RD 규칙 전부에 적용한다.
- 거절결정의 이유를 `대상 청구항(당시 번호) / 법조문 / 인용문헌과 조합 / 불리한 핵심 사실·차이점 / 판단 논리 / 결론` 단위로 나눈다. 거절결정 **이전**에 발송된 모든 의견제출통지서·최후통지의 해당 이유와 대조한다. 나중 문서나 거절결정 자체를 사전 통지로 취급하지 않는다.
- 확보된 통지서·거절결정서만으로 판정 가능한 사항은 의견서 원문이 없어도 끝까지 평가한다. 각 이유의 청구항·법조문·실제 인용문헌 식별자와 조합·구성 대비·핵심 논리를 날짜별로 연결하여 미통지 새 이유, 잘못된 문헌 조합, 대상항 불일치 및 결정서 내부 불일치를 찾는다. 의견서가 없다는 이유로 문서 대조 전체를 보류하거나 `의견서 원문 미확보로 확인 보류`를 관행적으로 적지 않는다.
- 통지서와 거절결정서만으로 청구항 보정 내역이나 의견서 반박을 알 수 없으면 청구항 번호·문구의 변화 원인을 추정하지 않는다. 새로운 이유가 실제로 사전 통지되지 않았는지는 **문서상 명백한 차이 / 조건부 점검 / 확인 불가**로 구분한다. 논리의 상세화와 새로운 핵심 사실·법적 근거를 구별한다. 법적 위법 여부는 문서만으로 단정하지 않는다.
- 출원인의 **핵심 주장을 심사관이 검토하지 않았다**는 평가는 해당 주장 원문이나 결정서에 명시된 주장 인용 등 확인 가능한 근거가 있을 때만 한다. 이 요건의 확인 불가가 다른 RD 규칙의 독립적 판단을 막지 않는다. 의견서 원문 확보 경로는 검증 전까지 스킬의 자동 다운로드 단계로 추가하지 않는다.

### 등록결정·등록 상태인 경우

- 거절결정서가 없고 등록결정 또는 등록 상태가 확인되면, KIPRIS Plus의 등록공보 PDF와 청구항 텍스트 API로 등록청구항 전체를 확인한다. 등록번호·등록일, 청구항 수·번호·원문과 종속관계 그래프를 확인한다. 등록공보를 기준으로 텍스트 API의 시점과 완전성을 검증한다. 불일치 시 출처를 밝히고 등록 원문 확인 전 법적 결론을 유보한다. 해당 공보 경로의 실제 호출은 아직 검증되지 않았으므로 실패 시 그 범위를 명시한다.
- 최종 유효 청구항 전체에서 선호·강조 표현의 잔존을 **RC-07**로 필수 점검한다. 명확성 하자가 남아 특허결정된 경우 `0511`을 명시한다.
- `references/registered-claim-rules.md`의 RC 규칙 전부를 적용한다. 제42조제4항제2호의 명확·간결성과 제42조제8항에 따른 시행령 제5조의 형식 요건을 **별개**로 판정한다. 적용 시점의 공식 법령 원문을 확인하고 조·항·호를 정확히 기재한다.
- 청구항 자체와 인용관계로 확인되는 사항을 우선 판정한다. 발명의 설명·도면이 필요한 정의, 위치, 작동관계는 가능 해석과 확인에 필요한 자료를 명시하고 조건부 점검한다. 단순 문법·어색한 표현, 결과적 등록, 이전 통지의 결론만으로 기재요건 위반을 단정하지 않는다. 등록청구항을 과거 통지서의 청구항으로 소급해 대조하지 않는다.
- 거절결정과 등록결정이 함께 보이는 이력이나 등록 후 정정이 의심되면 각 결정의 날짜와 현재 청구항의 기준 시점을 확인해 적용 범위를 밝힌다.

## 5. 결과

- 문서 목록 표: 공개공보·보정서·통지서(최후 여부 포함)·결정서·등록공보의 날짜, 발송/접수번호, 쪽수, PDF 링크, 검토 상태. 직권보정 없는 등록결정서는 PDF 링크 대신 `내용 확인·직권보정 없음·사용자 기준에 따라 미보관`으로 표시한다. 통지서마다 적용한 **청구범위 판본의 기준일·근거·보정 반영 여부**를 명시한다. 각 의견제출통지서의 OA 결과를 날짜별로, 거절결정서의 RD 결과 또는 등록청구항의 RC 결과를 별도 절로 제시한다. 등록 건은 등록번호·일자·청구항 출처와 확인한 청구항 전체 범위를 적는다.
- 발견마다 `규칙 ID / 판정(오지적·명백한 문서상 불일치·설명상 의문·조건부 점검·확인 불가) / 해당하는 진단코드 / 비교하는 각 문서의 쪽수·문구 / 차이 / 가능한 정합적 해석 / 판정을 가르는 누락 정보`를 기록한다. 진단코드는 원문 유형의 문서·결정 경과·다른 정당한 거절이유 유무 등 요건을 확인해 부여한다. 근거가 부족한 조건부 점검에는 확정 코드를 붙이지 않는다. 의문과 반론이 모두 가능한 사항을 조용히 삭제하지 않는다.
- 거절결정의 모든 핵심 근거가 어느 선행 통지의 어느 이유에 연결되는지 표시한다. 출원인에게 새로운 방어 쟁점이 생겼는지가 핵심이다. 발견이 없으면 `적용한 규칙에서 발견되지 않음`이라고 쓰며 무오류로 단정하지 않는다.
- RC 결과에는 청구항 번호·짧은 원문·정확한 근거 조항·명백한 위반/설명상 의문/조건부 점검/발견 없음의 판정·문맥상 해석·추가 확인 자료를 적는다. 형식 요건을 전수 확인했으면 점검한 범위도 명시한다.

## 규칙 추가

의견제출통지서 규칙은 `references/office-action-rules.md`에 OA-다음번호로, 거절결정서 규칙은 `references/rejection-decision-rules.md`에 RD-다음번호로, 등록청구항 규칙은 `references/registered-claim-rules.md`에 RC-다음번호로 추가한다. 진단코드의 정의와 부여 조건은 `references/diagnostic-codes.md`에서 관리한다. 각각 목적·필요 입력·검출·보류/예외·보고 예시를 넣고, 사례는 일반화 가능한 판정 절차와 구별한다. 수정 후 검증하고 저장한다.
