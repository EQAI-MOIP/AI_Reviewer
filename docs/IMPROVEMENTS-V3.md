# v3 개선 검토와 구현 결정

버전: 3.0.0 · 기준일: 2026-11-22 (Asia/Seoul)

## 1. 출력 8k가 충분한가

짧은 단일 항목에는 충분할 수 있으나, 다수 청구항·규칙·인용·코드 요건·반론을 한 번에 생성하는 진단에는 여유가 작다. 특히 OpenAI의 출력 상한은 보이는 텍스트만이 아니라 추론 등 비표시 토큰도 포함한다. 공식 추론 문서는 초기 실험에서 추론과 출력에 최소 25,000토큰의 여유를 권장한다.[1][2]

기본 출력은 32,768, 전체 요청 예산은 128,000으로 정했다. 이 값은 모델의 자동 검출된 한도가 아니라 사용자가 확인·조정하는 앱 설정이다. 규칙을 최대 3개씩 나누고, 출력 잘림·규칙 누락·청구항 검토 목록 누락을 검출하면 더 작은 묶음으로 재시도한다. 단일 규칙도 실패하면 해당 항목을 보류한다. 단순히 출력 상한만 높이는 것으로 검토 완결성을 선언하지 않는다.

입력 토큰 계산과 출력 예약의 합이 전체 예산에 맞는지 확인한다. PDF 입력 토큰을 계산할 수 없는 서버에서는 자동 추정으로 통과시키지 않는다. 입력을 요약해야 한 검토는 원문 전체 검토로 확정하지 않는다. 실제 출력·추론 토큰을 보고서에 기록하되, 실패한 요청 등 누락될 수 있는 사용량이 있어 금액 보증으로 사용하지 않는다.

## 2. HWPX·PDF를 제대로 읽는가

v2에서 HWPX 구역을 파일 이름순으로 처리하고 그림·수식 등 미해석 요소가 충분히 구분되지 않던 부분을 보강했다. v3는 한컴의 패키지 구조에 맞춰 `spine` 순서를 사용하고 문단 중간 표·중첩 문단의 순서를 보존한다. 구역·문단·표·행·셀을 기록하며, 실제 쪽수로 가장하지 않는다.[3][4]

PDF는 쪽별 문자 수·미판독 쪽·그림·미해석 글꼴·페이지 순서 복구 상태를 기록한다. 스캔 영역을 로컬에서 OCR했다고 표시하지 않는다. 필요할 때 PDF 지원 모델에 원문을 보내 전사하지만, 전사의 성공과 시각 대조는 별개로 둔다. 전사가 일부 실패하면 다음 검토에서 실패한 쪽만 재시도한다.

OpenAI의 PDF 입력은 텍스트뿐 아니라 페이지 이미지도 문맥에 포함하므로 입력 토큰이 커질 수 있다.[5] 이번 구현의 ‘2쪽씩 전사’는 출력 범위 요청이며, 원본 PDF 자체를 자르는 기능은 아니다. 매번 전체 PDF를 보내는 반복 입력 비용과 큰 파일 입력 한도는 남아 있다. 긴 스캔은 외부 PDF 도구에서 쪽 범위별로 나누어 추가해야 한다.

지원 내용과 미지원 내용의 전체 표는 `DOCUMENTS-V3.md`에 있다. 모든 실제 HWPX/PDF 변형의 판독 정확성을 검증했다는 의미는 아니다.

## 3. 파일은 어디에 남고 무엇을 지우는가

v2는 이전 사건 전체를 탭 내 ‘최근 작업’ 배열에 계속 보관했다. 사용자가 새 사건을 시작해도 원문 바이너리·추출문·결과가 남아 긴 사용에서 메모리가 누적될 수 있었다.

v3는 새 출원번호 조회·새 사건 준비·성공한 사건 가져오기 때 이전 사건을 정리한다. 문서 바이너리·본문·쪽 목록·로컬 전사본·구조 위치·판정·이력 참조를 해제하고 PDF iframe·Blob URL·다운로드용 URL을 정리한다. 실패한 가져오기는 기존 사건을 변경하지 않는다. 진행 중에는 사건 교체와 중복 업로드를 잠근다. 예시 보기의 백업은 실제 사건 하나로 제한한다.

브라우저의 다운로드 폴더에 이미 저장한 원문·보고서·사건 파일은 이 정리 대상이 아니다. 사용자 컴퓨터의 원래 업로드 파일도 삭제하지 않는다. 앱은 이들 파일의 임의 삭제 권한을 갖지 않는다. 현재 탭의 원문 크기와 180 MiB 한도, 즉시 비우기 버튼을 표시한다.

실제 RAM 사용량은 원문 크기보다 커질 수 있다. 자바스크립트 참조 해제 후 실제 회수 시점은 브라우저가 결정하며 메모리 안전 소거를 보증하지 않는다. 실행 도우미는 업무 문서를 디스크에 저장하지 않는다. 외부 LLM 제공자의 보관 정책은 탭 정리와 별개다.

## 4. Work 모드의 진단에 가까워지기 위해 필요한 과정

HTML/JavaScript라는 언어 자체가 법률·기술 추론의 수준을 정하는 것은 아니다. 판단의 기반은 연결된 모델, 확보한 원문, 시점 복원, 도구 연결과 검증 절차다. 이 앱에는 필요한 흐름을 코드로 명시했다.

1. 행정처리 이력과 실제 내려받은 문서 목록 대조.
2. 통지 당시 청구항 복원과 공개·등록·사후 보정 판본 분리.
3. 각 통지서별 OA, 거절결정과 선행 통지의 RD, 등록청구항 RC 검토.
4. 규칙과 전체 청구항의 검토 목록 확인.
5. 제안된 인용 문자열을 실제 문서 위치와 대조.
6. 코드의 결정 경과·다른 정당한 이유 등 조건을 별도로 확인.
7. 확정 후보에 대해 정합적 해석·예외를 별도 호출로 반론 검토.
8. 자료 누락·판독 미완료·요약 검토·판본 불확실성은 결과에 남겨 보류.

새 검증에서 모델의 청구항 목록이 없는데 ‘발견 없음’이 가능했던 경로, 청구항 범위는 미완료인데 후보 코드가 확정될 수 있던 경로를 재현하고 차단했다. 반론 검토는 같은 모델의 별도 호출이며 독립 전문가 검증이라고 표현하지 않는다.

제공된 스킬의 `SKILL.md`, `skill.json`, 네 종류 규칙·코드 참조 원문과 배포본 파일이 동일한 것을 확인했다. 키 파일은 읽어 진단하거나 포함하지 않았다. 기존 Work 진단과 정확도가 같다는 주장은 실제 평가 없이 하지 않는다.

남는 실무 조건은 적용 시점의 법령, 필요한 인용문헌·보정서·명세서의 접근 가능성, 실제 원문과 전사 결과의 대조, 모델의 충분한 한국어 특허 해석 능력이다. 실제 사건에 대한 운영 검증이 추가로 필요하다.

## 5. 큐리 애니메이션과 접근성

새 투명 WebP는 실제 1,254×1,254 픽셀의 4×4 배열이다. 네 장면마다 4프레임으로 인사, 입력 위치 안내, 서류를 읽는 대기, 정리 완료를 표현한다. 생성 목표보다 실제 반환 크기가 작아 2K·4K로 표시하지 않았다. 기존 큰 큐리 자산도 유지한다.

‘큐리와 둘러보기’는 문서 입력·출원번호·설정·원문 확인·진단·결과를 실제 화면 위치에서 안내한다. 작업 중에는 안내 투어를 막고 실제 단계 메시지와 경과 시간을 표시한다. 가상의 진행률이나 성공 상태를 표시하지 않는다. 시스템의 모션 줄이기, 앱의 모션 끄기, 화면 밖·숨긴 탭의 동작 정지를 지원한다.

## 6. 안정성과 시험 범위

중복 비동기 입력, 잘못된 import, 취소 직후 문서 추가, 이전 사건 참조 유지, 미리보기 URL 누적을 검사했다. 개별·전체 파일·추출 텍스트·압축 해제·XML 깊이·PDF 쪽·AI 호출 수에 한도를 둔다. HTTP 실패 응답의 본문도 취소하여 실패 후 연결을 붙잡지 않도록 했다.

확인한 시험 결과와 건너뛴 범위는 `VALIDATION.md`에 기록한다. 합성 자료·모의 API·실제 로컬 중계·컨트롤러 DOM 동작을 시험했지만, 개인 API 키를 사용하는 실제 KIPRIS·외부 모델 진단과 네이티브 브라우저 렌더링은 완료하지 않았다. 한계는 사용자에게 공개한다.
