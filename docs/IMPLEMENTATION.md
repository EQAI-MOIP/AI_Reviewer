## 실행 흐름

**내 문서로 진단:** 파일 추가 → 로컬 추출 → 종류·식별자 제안 → 심사관의 원문·판본 확인 → 로컬 예비 점검 또는 설정한 LLM의 문서별 규칙 검토 → 근거·코드 조건 확인 → 결과·보고서·사건 저장.

**출원번호로 조회:** KIPRIS 설정·13자리 출원번호 → 전체 이력 조회 → 발송번호가 일치하는 실제 PDF 확보 → 청구항 변동·공보 확보 → 위와 같은 원문·판본·규칙·근거 검토.

수동 입력 경로는 KIPRIS 키가 저장되어 있어도 자동으로 보조 조회하지 않습니다. 파일 추가만으로 원문을 LLM에 전송하지 않습니다. LLM 연결 전의 예비 점검은 규칙 전체의 심화 진단으로 표시하지 않습니다.

## 정확성을 위한 경계

문서 수집·판독·식별자·시점·판본·모델 검토·코드 조건을 별도로 확인합니다. 자동 제안은 원문 대조 후 문서 정보 수정 양식을 제출할 때 확인 상태로 반영합니다. 추정한 식별자를 같은 원문과 다시 비교한 결과만으로 검증 완료로 만들지 않습니다.

확정 판정은 실제 문서·쪽의 인용, 현재 비교 단위에서 사용할 수 있는 증거, 판독 범위, 대상 청구항과 판본, 결정 경과 등 해당 코드의 조건을 검사합니다. 앱이 원문에서 계산하는 조건을 모델이나 확인 체크의 주장으로 덮어쓰지 않습니다. 최후통지는 선행 통지 당시 청구범위도 비교 입력에 포함합니다.

다른 출원의 공보를 인용문헌으로 올릴 때는 **서류 준비 → 추가할 문서 종류 → 인용문헌**을 선택합니다. 인용문헌의 번호와 검토 사건 번호를 분리하며 서로 다른 사건의 통지·결정 문서를 같은 사건 원문으로 섞지 않도록 검사합니다.

조건부·확인 불가 후보는 심사관이 10~2,000자의 구체적인 사유를 기록해 제외할 수 있습니다. 원래 후보·근거·제외 이력은 유지하며, 제외가 부족한 원문이나 미완료 규칙의 검토를 완료시키지는 않습니다. 확정 반려사항을 같은 동작으로 임의 제외하지 않습니다.

## 데이터와 연결

API 키·설정·사건은 현재 탭 메모리에서 관리하고 자동 영구 저장하지 않습니다. 사건 JSON과 보고서는 사용자가 다운로드합니다. 키·설정은 사건 내보내기에 포함하지 않으며, 로컬 서버도 원문·키를 디스크에 저장하지 않습니다.

원본 기준에 따라 직권보정이 확인된 등록결정서만 원문 내보내기에 포함합니다. 직권보정이 없거나 미확인인 등록결정서의 원문과 인용은 보관 예외를 적용합니다.

모델 이름으로 별도 엔드포인트를 추정하지 않습니다. Responses와 Chat 요청 구조를 구분하며, PDF 원문 입력은 Responses와 입력 토큰 계산이 가능한 서비스에서 지원합니다. 기본 50,000토큰은 한 요청의 예산이며 사건 전체 비용 상한이 아닙니다.

## 한계와 검증 자료

원본 스킬과 동일한 정확성을 실증한 것은 아닙니다. 공식 법령 연혁의 자동 확보, 외국·비특허 인용원문의 범용 자동 검색, 완전한 PDF 시각 판독·OCR·자동 분할은 제공하지 않습니다. 부족한 원문·판본·법령 시점은 보류 조건으로 남습니다.

형식·크기·건수 한도와 실행 방법은 `../README.md`, API 세부 경로는 `API.md`, 검증 범위와 실제 결과는 `VALIDATION.md`를 따릅니다. 실제 업무 원문과 계정별 API를 사용한 진단 성능 평가는 구현 테스트와 별도의 확인 과제입니다.
