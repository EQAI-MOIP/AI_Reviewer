# v3 진단 과정과 검증 범위

기준: AI 심사팀장 큐리 3.0.0. 이 문서는 실제 구현된 동작과 시험 범위를 설명한다. 구현 위치는 `js/engine.js`, API 호출은 `js/api.js`, 규칙 원문은 `rules/` 및 `js/rules-data.js`이다.

## 1. 출력 8K 검토와 v3 처리 방식

v2의 기본 출력 상한은 8,192토큰이었다. 이것은 한 번의 API 응답 상한이며 앱 전체 보고서 길이 상한이 아니다. 다수의 거절이유, 청구항, 증거 인용과 JSON 필드를 한 번에 출력하면 상한에 먼저 도달할 수 있다. 추론 토큰을 출력 예산에 포함하는 공급자에서는 화면에 표시되는 문장보다 더 많은 예산이 필요할 수 있다. 지원 한도는 모델별로 확인해야 하며 모델 이름만으로 자동 추정하지 않는다.

v3 기본 설정은 요청 전체 예산 128,000토큰, 요청당 출력 상한 32,768토큰이다. 이 수치는 앱의 요청 설정이며 특정 모델이 이 한도를 지원한다는 선언은 아니다. 설정 화면에서 모델의 지원 한도에 맞게 낮추거나 높인다.

엔진은 다음과 같이 출력 실패의 영향을 제한한다.

- 문서별 OA·RD·RC 검토를 나누며, 기본 요청은 최대 3개 규칙이다.
- API가 `LLM_TRUNCATED`를 반환하면 규칙 묶음을 더 작게 분리한다. 잘린 JSON을 정상 결과로 복구하거나 완료로 표시하지 않는다.
- 한 규칙에서도 출력이 잘리면 해당 규칙을 확인 불가로 남기고 다른 규칙을 계속 검토한다.
- 응답이 요청한 규칙을 빠뜨려 `RULE_COVERAGE`가 발생한 경우도 작은 규칙 묶음으로 재시도한다.
- 입력 범위가 예산에 들어가지 않으면 먼저 규칙을 나누고, 이후 근거 보존 요약을 사용한다. 요약을 사용한 검토는 원문 전체 검토 완료로 확정하지 않는다.
- 요약 단계 출력 상한은 사용자 출력 설정과 16,384토큰 중 작은 값이다. PDF 전사 및 규칙 검토·반론 검토에는 사용자 출력 상한을 적용한다.
- 기본 LLM 요청 한도는 한 번의 실행에서 100회이며, `maxModelCalls`로 1~300회까지 설정할 수 있다. 실패한 요청과 재시도도 호출 수에 포함한다. 한도 초과 뒤 새 네트워크 요청을 보내지 않는다.

이 구조로 보고서가 요청당 출력 상한보다 길어질 수 있다. 높은 출력 상한을 설정했다고 그만큼 항상 출력되는 것은 아니며, 규칙 분할과 재시도는 API 사용량과 처리 시간을 증가시킬 수 있다.

## 2. 실제 진단 단계

### 원문과 시점 준비

KIPRIS 경로에서는 행정처리 이력·문서·청구항 변동 이력을 확보한다. 직접 업로드 경로에서는 제공된 자료와 사용자가 확인한 문서 종류·일자·출원번호·범위를 사용한다. 등록공보나 공개공보를 과거 통지 당시 청구항으로 자동 소급하지 않는다.

문서마다 텍스트, 원문 쪽 번호 또는 비물리적 본문 위치, 누락 쪽, 이미지·수식·생략된 콘텐츠 여부를 보관한다. PDF 쪽 순서가 복구 추정 상태이거나 HWPX·DOCX의 본문 구간만 확인된 경우 실제 쪽수로 인용하지 않는다.

### 규칙별 검토

각 의견제출통지서에는 OA 규칙을 독립적으로 적용한다. 거절결정서는 RD 규칙으로 선행 통지와 비교한다. 등록 건은 RC 규칙으로 최종 유효 청구항을 검토한다. 최후통지의 보정 전후 비교에는 각 시점의 청구범위를 별도로 포함한다.

모든 요청에 해당 검토 단위, 적용 판본, 기대 청구항 번호, 제공 문서별 쪽 목록, 원문 준비 상태를 전달한다. 모델에는 요청한 규칙을 각각 정확히 한 번씩 응답하도록 요구한다. 규칙 누락·중복, 알려지지 않은 코드, 발견 없음과 발견 항목의 충돌은 정상 결과로 받아들이지 않는다.

적용 판본의 청구항 번호가 확보되어 있고 적용 제외가 아닌 규칙은 `checkedClaims` 응답을 반드시 요구한다. 목록 자체가 없으면 작은 규칙 단위로 재시도하고, 다시 누락되면 확인 불가로 남긴다. 목록에 누락·추가·중복 번호가 있으면 해당 규칙과 반려 후보를 완료·확정으로 처리하지 않는다. 적용 제외 규칙은 구체적인 이유를 요구하며 목록은 선택적이다. 모델의 자기보고만으로 모든 청구항의 법적 검토 정확성을 보증할 수는 없다.

### 반론 재검토

원문 범위가 완전하다고 응답한 검토에서 모델이 `confirmed`로 제안한 항목은 별도 LLM 호출로 다시 검토한다. 두 번째 호출에는 첫 후보, 적용 규칙 및 해당 문서 단위의 원문을 제공한다. 가장 강한 정합적 해석, 예외, 판본 차이와 코드 부여 요건을 확인하도록 요청한다.

두 번째 호출은 `supported`, `conditional`, `disputed`로 답한다. 지지 판정에는 대상 문서의 실제 원문 인용이 필요하며, 인용은 보관된 해당 쪽의 문자열과 다시 대조한다. 원문에 없는 인용, 누락된 후보, 잘린 응답 또는 호출 한도는 재검토 완료로 인정하지 않는다.

의견이 엇갈린 후보는 삭제하지 않고 원래 근거와 반론을 함께 조건부 항목으로 남긴다. 두 모델 호출이 동의해도 출원번호·원문 가독성·당시 판본·결정 경과 등 코드의 다른 요건이 충족되지 않으면 확정 코드를 부여하지 않는다. 이 재검토는 별도 인간 검토나 독립된 공급자 검토를 뜻하지 않는다.

### 로컬 검증과 최종 상태

최종 판정은 모델의 문장만으로 정하지 않는다. 실제 근거 문자열, 문서 식별, 판본, 선행 통지의 날짜 순서와 코드 요건을 앱에서 검증한다. 청구항의 명시적 인용관계 및 선호·강조 표현은 로컬 보조 분석도 수행한다. 로컬 발견은 문맥 검토 전 조건부 후보이다.

`scopeComplete=true`와 함께 추가 원문 요청이 있는 모순된 응답은 완료로 처리하지 않는다. 큰 문서의 요약·일부 범위 검토도 완료로 처리하지 않는다. 미확인 문서, 미판독 쪽, 법령 시점, 조건부 발견, 실패한 단계가 남으면 결과에 명시한다.

## 3. PDF 전사

브라우저 자체 추출이 불완전하고 PDF 입력이 가능한 API가 설정되어 있으면, PDF 전사를 시도한다. 기본적으로 한 요청에서 실제 2쪽을 읽도록 요청하며, 출력이 잘리면 1쪽으로 나누어 다시 요청한다. `pdfPagesPerCall`은 코드 설정으로 1~4쪽을 허용한다.

PDF를 물리적으로 자르지는 않으므로 각 요청에 원본 PDF 전체가 전달된다. 쪽 범위를 나누어도 공급자의 입력 과금은 반복될 수 있다. 모델의 PDF 지원 여부와 입력 한도는 설정한 공급자 기준을 확인해야 한다.

요청한 쪽의 누락·중복·잘못된 번호·빈 전사·불확실성이 있으면 미완료로 남긴다. 실패한 쪽의 기존 로컬 추출문은 가능한 경우 유지하고, 성공한 다른 쪽도 보존한다. 일반적인 재진단에서는 실패·불확실한 쪽만 다시 전사하고 성공한 쪽은 재사용한다. 복구된 쪽의 과거 오류는 해결됨으로 남긴다. 전사가 완전하고 시각 대조만 남은 PDF는 재진단 때 다시 전사하지 않는다. 전사에 성공해도 `visualPending=true` 상태로 두어 실제 원문과 텍스트·도면·수식을 확인하도록 한다. 미판독 쪽이 남아 있으면 완료 체크박스로 우회할 수 없다.

## 4. 메모리와 실행량

한 사건은 최대 150개 문서, 개별 파일 30 MiB, 원문 바이너리 합계 180 MiB로 제한한다. 문서 본문은 개별 200만 자, 사건 전체 1,000만 자 제한을 적용한다. API 다운로드와 앱의 업로드 전 검사도 이 한도를 공유한다. 실제 브라우저 사용 메모리는 본문·파싱·Base64·화면 출력의 임시 사본 때문에 원문 합계보다 클 수 있다.

보고서에는 LLM 요청 시도·완료·실패 수와 공급자가 반환한 입력·출력 토큰, 보고된 추론 토큰을 기록한다. 추론 토큰은 출력 토큰의 부분집합으로 표시한다. 사용량을 반환하지 않은 요청이나 실패한 요청의 요금은 합계에 반영되지 않을 수 있으므로 비용 확정 자료로 사용하지 않는다. 토큰 수는 가격표와 직접 결합하지 않는다.

## 5. Work 모드와의 차이 및 남은 조건

앱이 LLM API를 호출한다고 ChatGPT Work의 파일 도구, 브라우저, 검색, 실행 환경, 스킬 실행기를 자동으로 사용할 수 있는 것은 아니다. 이 앱은 필요한 순서를 명시적인 JavaScript 과정으로 구현하고, 실제 자료를 모델 입력에 전달한다.

다음 조건은 여전히 결과의 품질을 좌우한다.

- 통지 당시 청구범위, 필요한 보정서, 발명의 설명·도면, 실제 인용문헌과 위치가 확보되어 있어야 한다.
- HWPX·DOCX를 읽었다는 사실과 수식·그림·물리적 쪽 위치까지 확인했다는 사실은 구별해야 한다.
- PDF 전사 정확성은 모델의 자기평가만으로 검증되지 않는다. 중요한 수식·표·식별자는 원문 확인이 필요하다.
- 공식 법령의 적용 시점 확인은 별도 자료와 사용자 확인이 필요하다. 본 앱은 범용 웹 검색 도구를 자동 제공하지 않는다.
- 입력 문서에 심어진 지시는 데이터로 취급하지만 모델의 모든 문서 해석 오류를 제거했다고 볼 수는 없다.
- 실제 키를 사용한 운영 API 검증과 실제 업무 자료의 판독 정확도 평가는 합성 단위시험과 별도로 수행해야 한다.

## 6. 시험

`node --test tests/engine-v3.test.cjs`는 다음 17개 위험을 합성 자료와 모의 API 응답으로 검증한다.

1. 최대 3규칙 분할과 출력 잘림 복구.
2. 한 규칙 실패 뒤 같은 묶음의 다른 규칙을 계속 처리.
3. 추가 원문 요청이 있는 응답의 완료 금지.
4. 명시적 청구항 검토 목록 누락 검출.
5. 별도 반론 검토 호출 및 실제 원문 제공.
6. 반론 불일치 후보의 원문 보존과 조건부 처리.
7. 두 번째 호출의 허위 인용 차단.
8. 요청 한도 뒤 네트워크 호출 중지와 미검토 규칙 기록.
9. PDF 2쪽→1쪽 전사 분할 및 원문 대조 상태 유지.
10. 실패한 PDF 쪽의 기존 텍스트 보존과 완료 우회 차단.
11. 복구된 PDF 쪽 순서·생략 콘텐츠의 품질 정보 유지.
12. 사건 원문 바이너리 180 MiB 한도.
13. v3 내보내기의 실행량·반론 기록 포함 및 요청 비밀정보 제외.
14. `checkedClaims` 목록 자체를 생략한 발견 없음 응답의 완료 차단.
15. 청구항 검토 범위가 불완전한 후보가 반론 지지로 승격되는 경로 차단.
16. 일반 재진단에서 실패한 PDF 쪽만 재전사하고 성공 쪽·원래 로컬 추출문을 보존.
17. 불확실한 PDF 전사 쪽의 재시도 및 성공 쪽 재사용.

기존 엔진 회귀시험도 함께 실행한다. 시험은 실제 공급자의 동작·특허 판단 정확도·모든 PDF/HWPX 변형에 대한 지원을 보증하지 않는다.
